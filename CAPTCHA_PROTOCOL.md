# Капча Black Russia — рабочий протокол

Снято с байткода `BrNewCaptcha` (classes4.dex, пакет `com.blackhub.bronline.game.gui.legacy`).
Ничего не подбиралось на живом аккаунте — формат читается прямо из APK, потому что
Java-часть капчи **сама собирает JSON и сама отправляет его через `sendJsonData`**.
В отличие от меню, где клиент шёл через натив и RPC, здесь весь путь виден в dex.

Проверено офлайн: локальный HTTP-сервер отдаёт картинку, решатель распознаёт,
в сессию уходит ровно `{"t":0,"s":"<текст>"}` в интерфейс 26.

---

## 1. Короткая версия

```
входящее : JSON интерфейс 26, ключ "u"  ->  URL картинки
ответ    : JSON интерфейс 26, {"t": 0, "s": "<текст с картинки>"}
```

Это **JSON-интерфейс, а не SA-MP диалог**. RPC 347/406 из `MENU_PROTOCOL.md` сюда
не относятся: у капчи нет ни `style`, ни кнопок, ни `info`. Идентификатор
интерфейса один и тот же в обе стороны — как у AUTH (38) и SPAWN_SELECT (50).

Один вариант. Других нет — см. §5.

---

## 2. Входящее

```json
{"o": 1, "u": "https://.../captcha.png"}
```

| Ключ | Что означает                                                    |
|------|-----------------------------------------------------------------|
| `u`  | **URL картинки**. Единственное поле, которое читает клиент      |
| `o`  | служебный, к капче отношения не имеет                           |

`o` в BR означает «открыть экран»: `GUIManager.onPacketIncoming` видит `"o"`,
зовёт `openingScreen(screenId, json)`. Без `"o"` пакет уходит в `onPacketIncoming`
уже открытого окна. Капче нужен именно `"o"`, иначе окно не создастся.

Цепочка в клиенте:

```
onPacketIncoming
  -> openingScreen(26, json)
     -> showGUI            удаляет старый json из кэша
        -> showCurrentGUI
           -> handleOtherScreen      (26 не фрагмент и не 13)
              -> createGuiFromId(26) -> BrNewCaptcha.newInstance()
                 -> show(json)
                    -> CaptchaURL = json.getString("u")
                    -> DownloadImageTask(url).start()
```

В `show()` читается ровно один ключ — `"u"`. Больше ничего из пакета не берётся.

**Картинки в APK нет.** Она всегда приходит с сервера по URL. Клиент качает её
через `FirebasePerfUrlConnection.openStream()` — обычный GET, без подписи и токенов,
поэтому скачивается обычным `urllib`.

---

## 3. Ответ

```json
{"t": 0, "s": "ab12"}
```

| Ключ | Тип   | Что означает                                    |
|------|-------|-------------------------------------------------|
| `t`  | int   | тип ответа. **Всегда `0`** — других значений нет |
| `s`  | str   | распознанный текст. Пустую строку не шлём        |

В APK **два** отправителя, и оба шлют одно и то же:

| Метод | Когда | Особенность |
|-------|-------|-------------|
| `BrNewCaptcha$2$1.run` | клик по «Готово» | через `Handler.postDelayed` — пауза 400 мс |
| `BrNewCaptcha$3.onDismiss` | окно закрылось | шлёт, если `dontSend == false` |

Оба вызывают `GUIManager.sendJsonData(26, json)` с ключами `t` и `s`.
Больше нигде в приложении интерфейс 26 не отправляется — проверено по всем 7 dex.

---

## 4. Поведение клиента, которое важно повторить

**Кнопка «Готово» неактивна, пока поле пустое.** `afterTextChanged` ставит
`alpha = 0.3f` (константа `1058642330` = `0.3f`) на пустом тексте и `1.0f`
на непустом. Клик при `alpha < 1.0` игнорируется.

**Задержка 400 мс.** `onClick` запускает анимацию `R.anim.button_click` и только
потом `postDelayed(...)` отправляет JSON.

**`close()` ставит `dontSend = true`** — программное закрытие окна не отправляет
ответ. А вот `onDismiss` от пользователя отправляет, даже с пустым полем.

Отсюда два правила для бота:

1. **Пустой ответ не отправлять.** Сервер засчитает его как неверный, а попытки
   не бесконечны.
2. **Не отвечать дважды на одну картинку.** Повтор может считаться второй попыткой.

## 5. Что проверено как нерабочее / несуществующее

| Вариант | Результат |
|---------|-----------|
| RPC 347 / 406 (как у меню) | не то: капча не SA-MP диалог, у неё нет style/кнопок |
| Ключ `"i"` как текст ответа | это поле других интерфейсов, у 26 его нет |
| Ключ `"t"` как текст ответа | `t` — это тип, всегда `0`; `{"t":100}` не ответ |
| Ключ `"d"`, `"code"`, `"captcha"` | в интерфейсе 26 не приходят |
| Другой id интерфейса | `getGuiId()` возвращает константу 26, других значений нет |
| Картинка внутри APK | её нет; всегда URL с сервера |
| Второй формат ответа | отсутствует: оба отправителя шлют `t`/`s` |

Один рабочий вариант. Это проверено статически, а не перебором — весь код капчи
лежит в dex и читается целиком.

## 6. Код

| Файл | Что там |
|------|---------|
| `logic/captcha.py` | `CAPTCHA_INTERFACE=26`, `from_interface`, `ImageUrlSolver`, `answer_payload`, `handle_captcha` |
| `bot.py` (`_on_receive_json`) | вызов `handle_captcha` на каждый JSON |
| `captcha_solver.py` | OCR: сегментация, нормализация, шаблоны |
| `captcha_templates.pkl` | 36 символов, 252 шаблона, 28×28 |
| `test_captcha.py` | 26 тестов, без сети и без аккаунта |
| `_apk/captcha_e2e.py` | сквозной офлайн-прогон: локальный сервер + реальный OCR |

### Как это встроено

`logic/captcha.py` уже содержал `SolverChain` с тремя видами капчи
(`packet_text`, `texture_image`, `manual`). Добавлен четвёртый — `image_url` —
как `ImageUrlSolver` в ту же цепочку. Старые пути не тронуты: `from_dialog`,
`from_text_draw`, `PacketTextSolver`, `RelaySolver` работают как раньше.

```
from_interface(26, {"u": url})  ->  CaptchaChallenge(kind="image_url")
  -> SolverChain -> ImageUrlSolver: скачать -> OCR -> текст
     -> CaptchaAnswerer.handle: пауза -> session.send_json(26, {"t":0,"s":текст})
```

Работает в фоновом потоке: скачивание и OCR занимают секунды, обработчик
пакетов блокировать нельзя.

### Лимит длины

`looks_like_answer` резал ответ до 8 символов — для капчи-картинки это мало.
Поле ввода в клиенте пускает до 20 (`maxLength=20`). Добавлен отдельный лимит
`FIELD_MAX_LEN = 20` для `KIND_IMAGE_URL`, старый лимит для пакетных капч сохранён.

## 7. Проверка

```bash
BR_TEST_MODE=1 python3 -m unittest test_captcha -v
BR_TEST_MODE=1 python3 _apk/captcha_e2e.py
```

`captcha_e2e.py` поднимает локальный HTTP-сервер, генерирует синтетическую капчу,
прогоняет полный путь и печатает, что ушло в сессию. Ожидаемый вывод:

```
истина: 'ab12'
   лог: [КАПЧА] ответ отправлен: 'ab12'
  перехвачено: True
  iid=26 payload={"t": 0, "s": "ab12"}
формат верный: True
совпало с истиной: True
ИТОГ: OK
```

## 8. Что осталось на живой прогон

Формат подтверждён кодом, но не сервером. На живом аккаунте проверить:

1. Приходит ли капча именно как iid 26 с ключом `"u"` — или как диалог
   (тогда сработает старый `from_dialog`).
2. Принимает ли сервер `dialog_id`/порядок — не применимо, тут JSON.
3. Точность OCR на реальном шрифте BR. На синтетике 97.9% по символам,
   на живом будет ниже. Лечится `captcha_solver.learn("видимый_текст", img_bytes)`.
4. Сколько попыток даёт сервер, прежде чем кикнуть.

Когда скажешь — прогоню на реальной капче.
