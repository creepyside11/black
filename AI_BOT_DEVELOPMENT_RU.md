## 0. Назначение и правила для ИИ

Этот документ предназначен ИИ, который получает задачу написать, изменить, объяснить или проверить сценарий для проекта black.
Его нужно использовать вместе с исходным кодом конкретной сборки, а не вместо кода и не как обещание, что сервер не изменился.
Проект — сетевой клиент с Python-логикой и Lua-мостом, а не скриптовый движок внутри APK игры.
Здесь описаны механизмы проекта, наблюдения в предоставленных записях и известные ограничения.
Сервер управляет состоянием мира и может отклонить или проигнорировать действие.
Отправка команды не равна выполнению действия и не равна получению награды.

### Шкала достоверности

- **КОД** — непосредственно следует из исходников этой сборки; в другой версии может отличаться.
- **ЗАПИСЬ** — наблюдалось в конкретном предоставленном видео или сетевом захвате; это не универсальный закон.
- **ПРОВЕРИТЬ** — гипотеза или условие, для которого не хватает подтверждения.
- **ПРИМЕР** — демонстрационные значения; не следует выдавать их за реальные данные сервера.
- При расхождении документа и установленной версии сначала изучить установленный код.
- Описание происходящего на экране сверять со временем и событиями; одно совпадение не доказывает причинную связь.
- Запрещено придумывать идентификаторы, поля пакетов, кнопки и подтверждения сервера.
- Если сведений недостаточно, сделать работающую инфраструктуру наблюдения и явно отметить недостающую механику.
- Не заявлять «проверено в игре», если проведены только unit-тесты, симуляция или анализ записи.
- Никогда не помещать в примеры реальные пароли, токены, персональные данные и содержимое капчи.

### Рабочий алгоритм ИИ

1. Выяснить режим: дополнение к работающему аккаунту или самостоятельный сценарий до входа.
2. Проверить наличие Lua-загрузчика и реальную структуру проекта.
3. Определить точное действие пользователя и необходимое серверное подтверждение.
4. Найти связанные интерфейсы, RPC, события и существующий код.
5. Разделить подтверждённые сведения и неизвестные параметры.
6. Записать состояния бота и переходы между ними.
7. Выделить координаты, таймауты и идентификаторы в конфигурацию.
8. Реализовать обработчики событий и отменяемые таймеры.
9. Не выполнять действия, для которых неизвестен протокол.
10. Протестировать синтаксис и поведение на фиктивных событиях.
11. Проверить конфликт с основным ботом и режимом `--own-ui`.
12. Для игрового теста сначала использовать наблюдение или `--dry`.
13. В отчёте отдельно перечислить офлайн-проверки и реальные игровые проверки.

## 1. Архитектура проекта

### 1.1. Основные части

- `bot.py` — консоль, аккаунты, жизненный цикл и подключение задач.
- `samp/` — сеть, структуры пакетов, RPC, интерфейсы и API клиента.
- `logic/` — рабочие сценарии, события, движение, спавн, распознавание интерфейсов.
- `logic/lua_engine.py` — запуск Lua-процесса, передача событий и выполнение действий.
- `logic/lua_runtime.py` — привязка событий аккаунта, очередь, таймеры и команда `/lua`.
- `logic/lua/harness.lua` — ограниченное окружение Lua и реализация таблицы `br`.
- `scripts/lua/` — каталог пользовательских Lua-файлов.
- `br/` — компоненты, связанные с приложением и протоколом Black Russia.
- `web/` — вспомогательные компоненты веб-интерфейса проекта, не игровой чат.
- `logic/farm_task.py` — существующая фермерская задача.
- `*_PROTOCOL.md` — отдельные заметки по исследованным механизмам.

### 1.2. Поток данных

1. Сервер отправляет данные сетевой сессии.
2. Сетевой слой отделяет пакет, RPC или интерфейс.
3. Парсер проекта извлекает поля.
4. Python выдаёт соответствующее событие.
5. Lua runtime помещает событие в очередь нужного аккаунта.
6. Lua-обработчик читает событие и снимок состояния.
7. Функции `br` формируют список предполагаемых действий.
8. После завершения обработчика Python обрабатывает этот список.
9. Ответ сервера приходит позднее в другом событии, если сервер отвечает.

### 1.3. Важное различие режимов

`addon` работает рядом с текущим аккаунтом и сам аккаунт не подключает.
`bot` подключает Lua до запуска аккаунта и затем запускает аккаунт.
В `bot` стандартная сетевая авторизация Python остаётся включённой.
В `bot` Lua управляет выбором спавна и интерфейсами, которые отданы под управление сценарию.
`--own-ui` включает управление интерфейсами и для дополнения.
В `addon` активная задача Python всё ещё может реагировать на те же события.
Сценарии с пересекающимся управлением могут отправить противоречивые действия.
Не путайте автономный Lua-сценарий с полной заменой сетевого клиента.
Для одного аккаунта одновременно поддерживается один активный Lua runtime.
У разных аккаунтов собственные runtime и отдельные очереди событий.

## 2. Установка и запуск

### 2.1. Termux

```sh
pkg update
pkg install python lua54 unzip -y
termux-setup-storage
mkdir -p "$HOME/black-lua"
unzip -o "$HOME/storage/downloads/black_lua_loader.zip" -d "$HOME/black-lua"
cd "$HOME/black-lua/black-lua-loader"
python bot.py
```

Имя архива и путь зависят от фактического расположения файла.
При первом запуске в начальном меню нажать `0`, чтобы перейти к консоли программы.
Проверить наличие Lua можно командами `lua5.4 -v`, `lua54 -v` или `lua -v`.
При необходимости указать путь через переменную `BR_LUA_BIN`.
Пример: `export BR_LUA_BIN="$PREFIX/bin/lua5.4"`.
Lua устанавливается отдельно: файл интерпретатора не входит в архив.
Исходное руководство указывает Python 3.10+ и Lua 5.4.
Наличие этой инструкции не доказывает, что текущая версия Termux проверена на конкретном телефоне.

### 2.2. Учётная запись и консоль

`/add СЕРВЕР НИК ПАРОЛЬ` — добавить собственный аккаунт согласно синтаксису проекта.
Пароль вводить локально и не добавлять в скрипт, документацию или общие логи.
`/list` показывает локальные идентификаторы аккаунтов.
`/start 1` запускает существующий аккаунт с ID 1.
`/stop 1` останавливает аккаунт с ID 1.
`/q` — выход из программы.
Точные доступные команды стоит сверять со справкой конкретной версии.
ID в `/lua` — локальный ID аккаунта проекта, а не игровой ID игрока.

### 2.3. Команды Lua

```text
/lua help
/lua list
/lua addon 1 hello_addon.lua
/lua addon 1 hello_addon.lua --dry
/lua addon 1 minigame_example.lua --own-ui
/lua addon 1 hello_addon.lua --packets
/lua bot 1 spawn_bot.lua
/lua bot 1 spawn_bot.lua --dry
/lua status 1
/lua reload 1
/lua stop 1
```

Все эти команды вводятся в консоли black, а не в игровом чате.
`/lua list` перечисляет `.lua` в `scripts/lua` и разрешённых подпапках.
`addon` можно прикрепить до или после входа, но вход он самостоятельно не запускает.
`bot` запускается до подключения аккаунта; при активном соединении его запуск отклоняется.
`--dry` блокирует изменяющие действия Lua и пишет их в лог.
При этом режим `bot --dry` всё равно может запустить подключение аккаунта.
`--packets` включает поток сырых входящих пакетов, который может быть очень большим.
`--own-ui` передаёт сценарию ответственность за соответствующие мини-игры и капчу.
Стандартные обработчики тех же интерфейсов при этом отключаются согласно логике сборки.
В режиме `bot` собственное управление интерфейсами включается автоматически.
`/lua status 1` показывает статистику и возможную потерю событий.
`/lua stop 1` останавливает Lua, но не обязательно весь аккаунт.
`/stop 1` нужен для остановки самого аккаунта.
Для перезагрузки сценария `bot` при активном соединении нужно сначала остановить аккаунт.
Путь к скрипту ограничен каталогом `scripts/lua`.
Неизвестный параметр команды приводит к ошибке.

## 3. Жизненный цикл Lua и события

### 3.1. Порядок работы

- Файл загружается в отдельный Lua-процесс.
- Определённые в нём функции регистрируются как обработчики.
- Затем вызывается `on_load`.
- В `on_load` соединение и данные аккаунта могут быть ещё недоступны.
- При режиме `bot` Python после запуска runtime начинает подключение аккаунта.
- По мере сетевых событий вызываются подходящие обработчики.
- Примерно каждые 0,25 секунды вызывается `on_tick`, если есть обработчик.
- Таймер `br.after` вызывает указанное имя события позже.
- `on_disconnect` сообщает о разрыве, но само восстановление нужно продумать отдельно.
- Остановка Lua не равна остановке сервера, аккаунта или всех глобальных настроек.

### 3.2. Общая форма обработчика

```lua
function on_event(e)
  br.log('Событие: ' .. tostring(e.name))
end

function on_chat(e)
  br.log('Чат: ' .. tostring(e.message))
end
```

Специальный обработчик имеет приоритет для своего события.
`on_event` служит общим обработчиком, если конкретный не определён.
Доступна и регистрация `br.event('on_chat', function(e) ... end)`.
Не рассчитывать, что два обработчика одного имени автоматически объединятся.

### 3.3. События и их аргументы

| Lua-событие | Поля `e` | Основание |
|---|---|---|
| `on_load` | `armed`, `script` | Запуск сценария |
| `on_tick` | `name` | Периодический вызов |
| `on_connect` | `name` | Событие подключения клиента |
| `on_disconnect` | `name` | Событие разрыва |
| `on_auth` | `state` | Стадия авторизации |
| `on_spawn_menu` | `data` | Пришло меню спавна |
| `on_spawn` | `name` | Клиент получил событие спавна |
| `on_json` | `interface_id`, `data` | Входящий интерфейс |
| `on_rpc` | `rpc_id`, `payload_hex`, `size` | Входящий RPC |
| `on_packet` | `packet_id`, `body_hex`, `size` | Только при `--packets` |
| `on_chat` | `message` | Сообщение, преобразованное клиентом |
| `on_dialog` | `id`, `style`, `title`, `text`, `button1`, `button2` | Обычный диалог |
| `on_npc_dialog` | `npc`, `text`, `model`, `buttons` | Диалог NPC |
| `on_notification` | `text`, `button`, `has_button` | Уведомление |
| `on_map_icon` | `id`, `position`, `marker_type`, `style` | Добавлена иконка карты |
| `on_map_icon_remove` | `id` | Удалена иконка карты |
| `on_checkpoint` | `x`, `y`, `z`, `radius` | Сервер задал точку |
| `on_checkpoint_clear` | `name` | Точка удалена |
| `on_textdraw` | `id`, `data` | Появление TextDraw |
| `on_textdraw_text` | `id`, `text` | Смена текста TextDraw |
| `on_textdraw_hide` | `id` | Скрытие TextDraw |
| `on_move_end` | `movement`, `status` | Завершение или отмена движения |
| `on_action_result` | `source`, `results` | Результат действий обработчика |

`on_spawn` — событие клиента; для уверенности в появлении в мире также проверяют позицию и признаки игрового состояния.
`on_move_end` отражает результат контроллера, а не гарантированную сервером досягаемость точки.
Поле `size` показывает исходный размер, а доступный hex может быть обрезан.
`on_action_result` не является серверным подтверждением.
Действия `on_load` в данной сборке не порождают обычный `on_action_result`.

## 4. Состояние и функции `br`

### 4.1. Чтение состояния

| Функция | Значение |
|---|---|
| `br.pos()` | Таблица `{x,y,z}` либо `nil` |
| `br.now()` | Монотонное время в секундах для интервалов |
| `br.connected()` | Признак соединения по данным сессии |
| `br.bot_id()` | Локальный ID аккаунта |
| `br.mode()` | `addon` или `bot` |
| `br.vehicle_id()` | ID транспорта или `nil` |
| `br.health()` | Известное здоровье или `nil` |
| `br.money()` | Известные деньги или `nil` |
| `br.interior()` | Интерьер или `nil` |
| `br.server_tail(n)` | Последние строки при наличии источника |
| `br.armed` | Разрешены ли изменяющие действия |
| `br.log(text)` | Вывести строку в лог |

Состояние представляет снимок на начало обработки события.
Повторный вызов `br.pos()` внутри одного обработчика не следует считать новым запросом к серверу.
Значение `nil` означает отсутствие данных, а не обязательно ноль.
`br.now()` не является точным временем на экране телефона.

### 4.2. Действия сценария

| Функция | Назначение |
|---|---|
| `br.walk(x,y,z)` | Начать пешее движение |
| `br.drive(x,y,z)` | Начать движение транспортом |
| `br.tp(x,y,z)` | Вызвать существующий способ перемещения проекта |
| `br.stop_movement()` | Остановить контроллер движения |
| `br.keys(keys,lr,ud)` | Установить кнопки и оси |
| `br.vehicle(id,seat)` | Запросить посадку; `br.vehicle(0)` — выход |
| `br.pickup(id)` | Взаимодействие с пикапом |
| `br.interact(id)` | RPC 436 с 32-битным ID |
| `br.select_textdraw(id)` | RPC 437 с 16-битным ID |
| `br.chat(text)` | Сообщение или команда игрового чата |
| `br.dialog(id,response,item,text)` | Ответить обычному диалогу |
| `br.npc(button)` | Ответить интерфейсу NPC 63 |
| `br.spawn_select(id)` | Выбрать ID из меню спавна |
| `br.send_json(iid,payload,packet_name)` | Отправить JSON интерфейсу |
| `br.send_rpc(id,payload_hex)` | Отправить RPC и шестнадцатеричное тело |
| `br.send_packet(id,payload_hex)` | Отправить сырой пакет |
| `br.solve_captcha(data)` | Передать данные встроенному решателю |
| `br.immortality(enabled)` | Включить или выключить существующую защиту проекта |
| `br.after(sec,name,data)` | Назначить будущее событие |
| `br.sleep(sec)` | Вставить задержку в очередь действий |
| `br.u16(n)`, `br.u32(n)` | Кодировать число в little-endian hex |
| `br.array(table)` | Пометить таблицу как JSON-массив |
| `br.null` | Представить JSON `null` |
| `br.event(name,fn)` | Зарегистрировать обработчик |
| `br.emit(action)` | Поставить поддерживаемое действие напрямую |

Возвращаемое значение функции действия означает постановку действия в список, а не успех на сервере.
Действия выполняет Python после возврата обработчика.
Для ожидания лучше использовать `br.after`, чтобы не занимать поток сценария.
У каждого действия проверять входные типы и диапазоны.
`br.immortality(true)` не гарантирует бессмертие: фактическое действие зависит от сервера.
Эта настройка может сохраниться после остановки Lua, поэтому её отключают отдельно при необходимости.
`br.tp` описывает функцию проекта, но успешное перемещение сервер не гарантирует.

### 4.3. Ограничения рантайма

- До 32 действий за один вызов обработчика.
- До 256 ожидающих таймеров.
- До 1000 событий в очереди runtime.
- `br.after` принимает задержку от 0 до 3600 секунд.
- Обычно обработчик ограничен примерно 2 секундами; загрузка имеет отдельный более длинный лимит.
- Большие события могут обрезаться перед передачей в Lua.
- Ограничение строк — до 4000 символов в преобразовании данных.
- Для массивов и объектов действует ограничение по числу элементов и глубине.
- В hex представлении передаются до 2048 байт, после обрезки возможен текстовый суффикс.
- Не используйте обрезанный hex как готовый исходящий пакет.
- Долгий обработчик или `br.sleep` задерживает события этого Lua-сценария.
- При переполнении события отбрасываются; смотрите `queue_dropped`.
- Один сценарий не должен бесконечно плодить повторные таймеры.
- `io`, `os`, `require`, `package`, `debug`, `load` и `dofile` не предоставлены.
- Ограниченное окружение не является полной гарантией безопасности недоверенного скрипта.

## 5. Игровой чат: формат и обработка

### 5.1. Три разных чата и команды

1. Консоль программы принимает команды вида `/lua ...`, `/start ...`, `/chat ...`.
2. Игровой чат передаётся серверу через `br.chat(...)` или `bot.api.sendchat(...)`.
3. Внешние интерфейсы, например мессенджеры или веб-страница, не следует считать игровым чатом без отдельной реализации.
4. `/lua status 1` — локальная консольная команда; через `br.chat` она уйдёт как игровая команда.
5. `/chat Привет` — команда консоли: она передаёт текст `Привет` активному аккаунту.
6. `br.chat('Привет')` — исходящее игровое сообщение.
7. `br.chat('/mm')` — исходящая игровая команда; её действие зависит от сервера.
8. Наличие команды в коде проекта не гарантирует, что она актуальна или доступна аккаунту.

### 5.2. Исходящее обычное сообщение: КОД

- `samp.api.sendchat` сначала проверяет соединение и непустую строку.
- Если первый символ сообщения не `/`, выбирается RPC `send_chat`.
- Константа `RPCConstants.CHAT` в сборке равна `414`.
- Тело `payload_send_chat` формируется как длина UTF-8 в одном байте, затем байты сообщения, затем нулевой байт.
- Длина измеряется в байтах UTF-8, а не количестве букв.
- Реализация отклоняет сообщение, если его UTF-8 длиннее 255 байт.
- Сообщения кодируются UTF-8 с `errors='ignore'` в Python.
- Другие версии протокола и серверные ограничения могут отличаться.

### 5.3. Исходящая команда: КОД

- Строка, начинающаяся непосредственно с `/`, направляется как `server_command`.
- В сборке `RPCConstants.SERVER_COMMAND = 378`.
- Тело: 32-битная длина UTF-8 и сами байты команды.
- Команда отправляется вместе с начальным `/`.
- Пробел перед `/` меняет классификацию: такая строка уже не начинается со слеша.
- Пустая строка не отправляется.
- Подтверждение применения команды нужно искать отдельно среди событий сервера.
- Не следует конструировать эти пакеты вручную, когда достаточно `br.chat`.

### 5.4. Входящее сообщение: КОД

- Используется RPC `client_message`, константа которого в сборке — `360`.
- Парсер пропускает первые 32 бита и далее читает 32-битную длину и UTF-8-строку.
- В текущей реализации пропущенное значение в Lua-событии не сохраняется.
- Результат парсинга содержит поле `message`.
- Далее клиент вызывает Python-событие `onShowChat`.
- Lua runtime преобразует его в `on_chat` с полем `e.message`.
- Значение — готовый текст сообщения, не таблица игрока с гарантированными `nickname` и `text`.
- Имя автора, канал, цвет и текст не следует считать структурно выделенными полями.
- Сетевые сообщения других типов могут приходить через иные события.
- Эта схема описывает данный парсер, а не все потенциальные виды чата игры.

### 5.5. Цветовые и служебные теги

Текст может содержать форматирующие последовательности или серверные префиксы.
Если в записи наблюдаются теги вида `{RRGGBB}`, их можно убрать для поиска по тексту.
Это пример распространённого формата; наличие тегов в каждом конкретном сообщении нужно подтвердить.
Сохраняйте оригинал для диагностики, но не выводите пароли или приватные данные.

```lua
local function normalize_chat(value)
  local s = tostring(value or '')
  s = s:gsub('{%x%x%x%x%x%x}', '')
  s = s:gsub('%s+', ' ')
  return s
end

function on_chat(e)
  local text = normalize_chat(e.message)
  if text:find('ПРИМЕР ТЕКСТА', 1, true) then
    br.log('Совпало заранее проверенное сообщение')
  end
end
```

`ПРИМЕР ТЕКСТА` необходимо заменить строкой, реально полученной на целевом сервере.
Функция `string.find(..., 1, true)` ищет буквальный текст, а не шаблон Lua.
Сравнение чувствительно к регистру и возможным различиям написания.
Встроенное преобразование регистра Lua не гарантирует корректное изменение русских букв в UTF-8.
Для чисел учитывать десятичную точку, запятую, разделители разрядов и посторонние теги.
Не считать каждое вхождение слова «успешно» подтверждением своей операции.
Сопоставлять сообщение с текущим состоянием, сроком ожидания и другими признаками.

### 5.6. Диагностический чат-скрипт

function on_load(e)

end

function on_chat(e)

Не отправлять в чат автоматические сообщения только ради проверки обработчика.

## 6. Сетевые интерфейсы и JSON

### 6.1. Устройство интерфейса

Пакет интерфейса имеет идентификатор `0x1B` согласно `samp/constants.py`.
Сборщик `build_json_packet` записывает байт типа, 16-битный ID и 32-битную длину.
Числа ID и длины записываются little-endian.
Далее следуют байты JSON в UTF-8.
Это описание именно сборщика проекта, а не обещание совместимости со всеми версиями игры.
ID интерфейса и ID RPC — разные пространства идентификаторов.
Тип `0x1B` тоже не является ID конкретного интерфейса.
Поле `size` — размер UTF-8 в байтах, а не число символов JSON.
Ключи JSON чувствительны к регистру и типу значения.
`1`, `true` и строка `'1'` не являются взаимозаменяемыми.

### 6.5. JSON и Lua-таблицы

```lua
local object = {}
local array = br.array()

```

Пустая обычная таблица кодируется как `{}`.
Для пустого массива `[]` использовать `br.array()`.
JSON `null` представлен специальным `br.null`, а не обычным отсутствующим полем.
Lua `nil` удаляет ключ таблицы и не равен явному JSON `null`.
Числовые ключи могут иметь другую семантику, чем строковые ключи.
Не смешивайте массив и объект в одной таблице без проверки сериализации.

## 7. RPC, пакеты и бинарные поля

### 7.1. Что означают названия

- Пакет — единица транспортного протокола, видимая в сетевом слое.
- RPC — отдельный тип удалённого вызова в протоколе клиента.
- Payload — тело сообщения без необходимости включать внешний транспортный заголовок.
- ID объекта — идентификатор, назначенный сервером; не следует путать его с ID RPC.
- TextDraw ID — идентификатор UI-элемента, потенциально меняющийся между событиями.
- Interface ID — ID JSON-интерфейса, не ID кнопки.
- У каждого отправителя могут быть параметры надёжности, приоритета и канала.
- При воспроизведении недостаточно знать только визуальный текст и тело.

### 7.2. Известные вызовы проекта

| Операция | ID / построение | Примечание |
|---|---|---|
| Входящее сообщение чата | RPC 360 | Парсер возвращает `message` |
| Обычный исходящий чат | RPC 414 | Длина uint8, UTF-8, завершающий ноль |
| Исходящая команда | RPC 378 | Длина uint32 и UTF-8 |
| Взаимодействие | RPC 436 | `br.interact(id)` использует uint32 LE |
| Выбор TextDraw | RPC 437 | `br.select_textdraw(id)` использует uint16 LE |

Числа относятся к предоставленной версии проекта и должны сверяться с исходниками текущей версии.
Не всякий UI-объект нажимается RPC 437, а не всякий игровой объект — RPC 436.

### 7.3. Кодирование числа

```lua
local encoded16 = br.u16(2052)
local encoded32 = br.u32(2052)
br.select_textdraw(2052)
-- Эквивалентная форма только для этого RPC:
br.send_rpc(437, encoded16)
```

Число 2052 здесь демонстрационное; это не универсальный ID яблока.
Не отправлять оба вызова: они показаны как альтернативные формы.
Не воспроизводить обрезанные сетевые данные и пакеты из другой версии клиента.
Большой raw-пакет может не поместиться в ограничение моста.

## 8. Спавн и начало сессии

### 8.1. Последовательность

1. Создать или выбрать локальный аккаунт.
2. Убедиться, что аккаунт отключён для режима `bot`.
3. Запустить Lua-сценарий командой `/lua bot ...`.
4. Python запускает сетевую сессию и свою авторизацию.
5. Дождаться `on_spawn_menu`.
6. Взять доступные ID из фактического `e.data`.
7. Выбрать проверенный ID через `br.spawn_select`.
8. Дождаться `on_spawn` и доступной позиции.
9. Проверить, не открыта ли заставка или другой обязательный интерфейс.
10. Только затем переходить к маршруту и рабочей задаче.

### 8.2. Пример выбора первого предложенного ID

```lua
function on_spawn_menu(e)
  local options = e.data and e.data.m
  if type(options) ~= 'table' then return end
  local first = options[1]
  if type(first) ~= 'number' then return end
  br.after(2, 'choose_spawn', {id=first})
end

function choose_spawn(e)
  br.spawn_select(e.id)
end

function on_spawn(e)
  br.log('Клиент сообщил о спавне; проверяю позицию')
end
```

Это соответствует примеру из архива, если `m` действительно массив числовых ID.
Если сервер присылает объекты или другую структуру, скрипт нужно изменить на основании фактического события.
Первый пункт не гарантирует нужную географическую точку.
Два похожих метода выбора спавна в разных частях проекта могут иметь разные формы payload.
При использовании Lua выбирать `br.spawn_select` и читать реализацию `logic.spawn`.
Не придумывать постоянные ID точек между серверами и аккаунтами.

## 9. Движение, маршруты и транспорт

### 9.1. Координаты и позиция

- Координата состоит из `x`, `y`, `z` в системе мира игры.
- Нужны значения именно из текущей карты, интерьера и версии проекта.
- Совпадение X/Y при разном Z может означать этаж или другую область.
- Для интерьеров учитывать идентификатор интерьера, если известен.
- Позиция `nil` означает, что клиент пока не получил надёжную позицию.
- Позиция из скриншота доказывает наблюдаемое положение, но не вход в серверный триггер.
- Погрешность и частоту обновления позиции необходимо измерить.
- Достижение точки сравнивать с радиусом, а не требовать точного равенства float.

### 9.2. Маршрут как набор опорных точек

```lua
local route = {
  {x=100.0, y=200.0, z=15.0},
  {x=120.0, y=230.0, z=15.0},
}
```

Эти координаты вымышлены и служат только примером структуры.
Опорные точки нужны на поворотах, развязках, входах и других неоднозначных местах.
Не всегда нужно фиксировать каждый миллиметр поворота, но редкие точки могут срезать путь.
Точность движения зависит от реализации контроллера и самого сервера.
Держите пеший и автомобильный маршруты отдельно.
После дисконнекта повторно определяйте местоположение вместо слепого продолжения.
После смены интерьера перепроверяйте координаты и следующую цель.
Маршрут должен поддерживать таймаут, отмену и обнаружение застревания.

### 9.3. Последовательное прохождение

```lua
local index = 1
local route = {
  {x=100, y=200, z=15}, -- пример
  {x=120, y=230, z=15}, -- пример
}

local function next_point()
  local p = route[index]
  if not p then br.log('Пример маршрута завершён'); return end
  br.walk(p.x, p.y, p.z)
end

function on_spawn(e)
  next_point()
end

function on_move_end(e)
  -- Это упрощённый шаблон: в реальном сценарии проверить e.status,
  -- состояние задачи, фактическое положение и тип движения.
  br.log('Контроллер сообщил о завершении движения')
end
```

Пример намеренно не продвигает индекс автоматически, потому что нужно знать формат `status` конкретной версии.
Автоматический переход без проверки `status` способен считать отмену успешным прибытием.
Для транспортного пути `br.drive` требует подходящего состояния и транспортного средства.
`br.vehicle(id,seat)` отправляет действие посадки, но факт посадки нужно подтвердить.
`br.vehicle(0)` запрашивает выход, но результат также должен быть подтверждён.
Значение `seat` и доступность конкретного транспорта определяются текущей реализацией и состоянием мира.

## 10. Ферма и сбор яблок: известные данные

### 10.1. Что известно

- Пользователь сообщил, что имеющийся сценарий успешно устраивается на работу, но мини-игра не срабатывала.
- В одной записи наблюдались действия по сбору двух деревьев.
- В записи встречались исходящие нажатия RPC 437, сгруппированные в две серии по десять.
- Входящее событие показа TextDraw с именем `gui:fruitpickerapple` связано с актуальным яблоком.
- В коде проекта для исследования этого поведения нужно изучать обработчики TextDraw и фермы.
- Предварительное создание элементов и фактический показ конкретного элемента — разные стадии.
- ID, объявленные заранее, не доказывают, какой элемент активен прямо сейчас.
- На основании наблюдения стоит связывать показ активного TextDraw с последующим выбором ID.
- Точные ограничения и последовательность нужно перепроверить на текущем сервере.
- В разобранном фрагменте зафиксирован прогресс до 2,0 кг; полный цикл сдачи не подтверждён.
- Скриншот пользователя отдельно показывает счётчик 0,0 / 5,0 кг и затем 0,1 / 5,0 кг.
- Из разных фрагментов нельзя автоматически делать вывод об одном и том же полном цикле.

### 10.2. Что остаётся неизвестным

- Универсальная формула размещения яблока и постоянство ID между сессиями.
- Действительное количество деревьев до полного рюкзака для любой фермы.
- Что именно подтверждает успешную сдачу и зачисление денег в текущей версии сервера.
- Можно ли восстановить задачу после отключения, не ошибившись с текущим деревом.
- Все изменения игровых интерфейсов после создания записи.
- Путь от любого возможного спавна до фермы.

### 10.4. Предлагаемые состояния

1. `WAIT_WORLD` — ожидание появления в мире.
2. `GO_TO_JOB` — движение к подтверждённой точке работы.
3. `APPLY` — начало устройства; ждать серверный результат.
4. `GO_TO_TREE` — переход к дереву.
5. `WAIT_APPLE` — ожидание актуального элемента.
6. `SELECT_APPLE` — выбор ID из актуального события.
7. `WAIT_UPDATE` — ожидание изменения интерфейса или счётчика.
8. `GO_TO_DROPOFF` — переход к точке сдачи при подтверждённом условии.
9. `WAIT_DROPOFF` — ожидание сообщения/изменения состояния.
10. `PAUSED` — неизвестное состояние, ошибка или требование вмешательства.

Эта схема — проектирование, а не доказательство того, что каждый переход уже реализован или подтверждён.
Нельзя повторно выбирать один и тот же ID без учёта скрытия/обновления элемента.
Необходимо проверить, сколько активных элементов может одновременно существовать.
При потере события лучше остановиться и запросить повторную синхронизацию, чем перебирать ID.

### 12.2. Как можно искать цель по расстоянию

При наличии координат игрока и численного расстояния возможна оценка положения по измерениям из разных точек.
Три не лежащие на одной прямой точки могут помочь определить положение на плоскости при подходящей модели расстояния.
Это математическая гипотеза, не подтверждение того, как работает конкретный игровой индикатор.
Нужно проверить шум, округление, обновление, препятствия, высоту Z и относится ли значение к ближайшему кладу.
Если измерение округлено до метров, возможна область решений вместо одной точной точки.
Если клад перемещается или источник переключается на другой, обычная оценка может ошибаться.
Практический сценарий должен ограничивать число попыток, проверять близость и уметь остановиться.

## 15. Таймеры, случайность и остановка

`br.after` добавляет событие, а не ждёт окончания таймера внутри обработчика.
Применяйте его для повторной проверки условий, а не как единственное доказательство успеха.
В `on_disconnect` сбрасывайте состояние, которое зависит от текущей сессии.
Для каждого таймера храните номер поколения или иной идентификатор операции.
Установите верхний предел ожидания серверного ответа.
При истечении таймаута переводите задачу в понятное состояние ошибки или паузы.
Случайные задержки полезны для моделирования временных допусков, но не гарантируют успешность действий.
Взаимодействие должно начинаться только после того, как игра готова принять действие.
Остановка сценария должна отменять будущие действия и прекращать движение, если это необходимо.
Проверяйте, какие настройки сохраняются после остановки: например, защита от голода может остаться включённой.
Длительность часовой работы следует измерять через `br.now()`, а не предполагаемое число тиков.
Перед остановкой через час уточнить, нужно ли завершить текущую операцию или остановиться немедленно.

### 15.1. Пример таймера длительности

```lua
local deadline = nil
local expired = false

function on_load(e)
  deadline = br.now() + 3600
end

function on_tick(e)
  if expired or not deadline then return end
  if br.now() >= deadline then
    expired = true
    br.stop_movement()
    br.log('Прошёл час: движение остановлено, дальнейшая работа не запускается')
  end
end
```

Пример сам по себе не отключает аккаунт и не гарантирует корректного завершения игровой операции.
Остальная логика обязана проверять `expired` до постановки новых действий.
Если время работы считать только после спавна, задайте `deadline` в подтверждённом состоянии, а не в `on_load`.

### Настройки скрипта из панели VPS

Панель сохраняет для каждого Lua-файла свой JSON с несекретными параметрами. Используйте `br.setting('имя', значение_по_умолчанию)` или `br.settings()` для всей таблицы. Поддерживаются строки, числа, булевы значения, списки и вложенные JSON-объекты с произвольными названиями ключей. Обрабатывайте отсутствие ключей, используйте разумные значения по умолчанию и не предполагайте, что панель автоматически изменяет код.

Галочка панели включает или отключает передачу настроек целиком. При отключении `br.settings()` возвращает пустую таблицу, а `br.setting` возвращает значение по умолчанию; сам скрипт продолжает работать. Для выключения отдельной функции используйте булев параметр и проверяйте его в обработчике. Не помещайте API-токены в настройки скрипта: для автокапчи есть отдельный защищённый раздел.
