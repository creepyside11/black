# Меню Black Russia — рабочий протокол

Проверено на живом сервере **NOVGOROD** (`80.66.82.34:5125`), аккаунт `Sha_Pismenskij`,
через socks5-прокси `127.0.0.1:20013`. Всё, что ниже — снято с работающего обмена,
а не выведено из догадок. Если когда-нибудь перестанет отвечать — в конце есть
раздел «Как перепроверить», тем же способом находится новое значение за один прогон.

---

## 1. Короткая версия

Меню в BR — это **SA-MP диалог, но с другими номерами RPC**.

```
входящее меню : RPC 347   (не 61, как в обычном SA-MP)
ответ         : RPC 406   (не 62, как в обычном SA-MP)
доставка      : RELIABLE + SYSTEM_PRIORITY
payload ответа: как в SA-MP DialogResponse, без изменений
```

Ответ собирается так:

```python
from samp.packets import RPCBuilder, PacketBuilder

# dialog_id=0, кнопка «Выбрать» (response=1), строка №0
packet = PacketBuilder.rpc_build("dialog_response", 0, 1, 0, "")
session._sender.send(packet, rpc_name="dialog_response")
```

Или штатно, через сессию:

```python
session.send_dialog_response(dialog_id=0, response=1, list_item=0, text="")
```

Это всё. Остальное в файле — почему именно так и что уже проверено как нерабочее.

---

## 2. Входящее меню — RPC 347

Payload читается последовательно, little-endian. Реальный дамп `/mm`:

```
0000 02 34 7b4530353834427d... 0e d092... 0e d097... b8010000 ...
```

| Поле        | Тип       | Пример (реальный)                    | Что это                                   |
|-------------|-----------|--------------------------------------|-------------------------------------------|
| `dialog_id` | `uint16`  | `0`                                  | id диалога. **У BR всегда 0** — см. §5    |
| `style`     | `uint8`   | `2`                                  | стиль диалога, `2` = список строк         |
| `title`     | `uint8` len + UTF-8 | 52 байта → `{E0584B}BLACK RUSSIA {ffffff}\| Меню игрока` | заголовок окна |
| `button1`   | `uint8` len + UTF-8 | 14 байт → `Выбрать`                  | левая кнопка                              |
| `button2`   | `uint8` len + UTF-8 | 14 байт → `Закрыть`                  | правая кнопка                             |
| `info`      | `uint32` len + UTF-8 | 440 байт → строки через `\n`        | тело: список пунктов или текст            |

Контроль сходимости: `2 + 1 + 1 + 52 + 1 + 14 + 1 + 14 + 4 + 440 = 530` — ровно длина
реального пакета. Значит раскладка верная, ничего не потеряно.

**Строки списка** лежат в `info`, по одной на строку, с цветовыми кодами:

```
{E0584B}1. {ffffff}Статистика
{E0584B}2. {ffffff}Список команд
{E0584B}3. {ffffff}Личные настройки
{E0584B}4. {ffffff}Настройки безопасности
{E0584B}5. {ffffff}Жалоба/Вопрос
{E0584B}6. {ffffff}Улучшения
{E0584B}7. {ffffff}Правила сервера
{E0584B}8. {ffffff}Изменить имя
{E0584B}9. {ffffff}Промокод
{E0584B}10. {333cc66}Донат
```

Номер пункта в тексте (`1.`, `2.`, ...) — **это не индекс**. Индекс считается
с нуля по порядку строк и уходит в `list_item`. Поэтому «1. Статистика» → `list_item=0`,
«2. Список команд» → `list_item=1`.

Цветовые коды (`{RRGGBB}`) перед разбором надо вырезать — `logic/menu.py:strip_colors`.

## 3. Ответ — RPC 406

Payload — байт в байт стандартный SA-MP `DialogResponse`. Ничего выдумывать не нужно,
меняется **только номер RPC**:

| Смещение | Тип       | Поле        | Что означает                                                     |
|----------|-----------|-------------|------------------------------------------------------------------|
| 0        | `int16`   | `dialog_id` | id диалога из входящего пакета. У BR `0`, и это работает          |
| 2        | `uint8`   | `response`  | **1 = левая кнопка** (`Выбрать`), **0 = правая** (`Закрыть`)      |
| 3        | `uint16`  | `list_item` | **индекс выбранной строки, с нуля**. Для полей ввода — 0          |
| 5        | `uint8`   | `text_len`  | длина текста в байтах UTF-8 (не в символах)                       |
| 6        | `text_len`| `text`      | текст из поля ввода. Для списков пустая строка                    |

Готовые payload'ы:

```
li=0 resp=1  ->  00 00 01 00 00 00      # выбрать первую строку
li=1 resp=1  ->  00 00 01 01 00 00      # выбрать вторую строку
li=0 resp=0  ->  00 00 00 00 00 00      # закрыть
```

Полный пакет для `li=0 resp=1` (конверт собирает `RPCBuilder`, руками не трогать):

```
0b 96f1 8000 0008 0000 000001000000
^  ^^^^                          ^^^^^^^^^^^^ payload (6 байт)
|  RPC id 406, записан 9 битами
PacketID.RPC = 0x0B
```

### Доставка

`RELIABLE` + `SYSTEM_PRIORITY` (`samp/sender.py`, ключ `"dialog_response"`).
На `MEDIUM_PRIORITY` сервер пакет принимает, но обработчик его не видит — проверено,
молчит. Это же требование, что и у спавна.

---

## 4. Что за что отвечает — сводка по полям

Чтобы больше не гадать, вот назначение каждого поля в обе стороны.

### Входящее (RPC 347)

| Поле      | За что отвечает                                                        |
|-----------|------------------------------------------------------------------------|
| `dialog_id` | какой диалог отвечаем. У BR **всегда 0**, различать диалоги по id нельзя |
| `style`   | `2` — список пунктов; `0` — просто текст; `4`/`5` — списки с табами     |
| `title`   | по нему определяется, что за экран: «Меню игрока», «Статистика игрока»  |
| `button1` | подпись левой кнопки — обычно `Выбрать`                                 |
| `button2` | подпись правой кнопки — обычно `Закрыть`                                |
| `info`    | **главное поле**: список пунктов (style 2) либо данные (статистика)     |

### Исходящее (RPC 406)

| Поле        | За что отвечает                                                     |
|-------------|---------------------------------------------------------------------|
| `dialog_id` | привязка ответа к диалогу. `0` работает, потому что и входящий `0`  |
| `response`  | **какая кнопка нажата**: 1 — левая (`Выбрать`), 0 — правая (`Закрыть`) |
| `list_item` | **какой пункт выбран**, индекс с нуля. Не номер из текста строки     |
| `text`      | только для полей ввода (промокод, сумма, ник). Для списков `""`      |

Правило, которое легко перепутать: `response` — это **кнопка**, `list_item` — **строка**.
Они независимы. Выбрать строку 3 левой кнопкой = `response=1, list_item=3`.

## 5. Почему `dialog_id = 0` — это нормально

Соблазн решить, что «id 0 — значит диалог не распознан, нужен настоящий id».
Нет. В RPC 347 первым идёт `uint16`, и в реальном пакете там честные `00 00`.
Сервер сам присылает `0` и сам же принимает `0` в ответе.

Практическое следствие: **все диалоги BR имеют один id**, поэтому «тот же диалог
или новый» определяется не по id, а по содержимому — заголовок + тело.
В коде это `logic/menu.py:dialog_signature(style, title, info)`.

## 6. Что проверено как НЕРАБОЧЕЕ

Этот список — главная ценность файла. Всё ниже я гоняла на живом сервере,
и всё это не закрывает диалог. Не повторять.

### RPC с неверным номером

| Отправлялось | Результат |
|--------------|-----------|
| RPC **514** | не влезает в 9 бит RPC-заголовка, уходит как RPC 2 (внутренний пинг) |
| RPC **62**  | стандартный SA-MP `DialogResponse` — у BR не работает |
| RPC **61**  | стандартный SA-MP `ShowDialog` — не работает |
| RPC **343, 346, 347, 348, 349** | мимо, реакции нет |
| RPC **406** | **работает** |

### JSON вместо RPC

Ответ через `USER_INTERFACE_SYNC` (packet `0x1B`), интерфейс 10:

```python
session.send_json(10, {"r": 1, "i": "2. Список команд", "l": 0})
```

Перебрано: с `l` и без `l`, `i` текстом и `i` индексом, `l` = 0/1/2,
плюс лишние поля `id`, `d`, `di`, `dlg`, `t`, `s`, `c`. **Ни один вариант
диалог не закрывает.** Сервер продолжает считать диалог открытым.

### Почему JSON-путь вообще возник

Разбор APK дал `BrDialogWindow.sendResponse`, который собирает
`{"r":…, "i":…, "l":…}` и зовёт `GUIManager.sendJsonData(10, json)`.
Выглядело как готовый ответ. Но:

- в APK нет ни одного другого класса с ключами `r`/`i`/`l` — 264 вызова
  `sendJsonData` по всем 7 dex, и только этот один;
- в `libblackrussia-client.so` **нет обработчика SA-MP-диалога вообще**
  (нет `ScrShowDialog`, нет `DialogBox`);
- `sendJsonData` в нативе — обычный JNI-синглтон без разбора screenId,
  то есть маршрутизацию делает C++-ядро, а не Java.

Вывод: это **клиентская** реализация того же диалога поверх нового GUI.
Java шлёт JSON своему же нативу, натив превращает его в RPC 406 и отправляет
на сервер. Мы шли сразу на сервер, минуя натив, — поэтому JSON и не работал.
Правильный слой — RPC.

## 7. Как перепроверить, если однажды отвалится

Оракул нашёлся сам и он очень удобный.

**Пока диалог открыт, сервер на `/mm` отвечает уведомлением `Закройте диалог!`
(JSON интерфейс 13, ключ `i`).** Значит состояние диалога видно снаружи:

```
отправили вариант ответа -> /mm
  пришло НОВОЕ меню (RPC 347)      -> вариант сработал, диалог закрылся
  пришло «Закройте диалог!»        -> вариант не принят
  тишина                           -> смотреть отдельно, обычно сессия мертва
```

Скрипты для этого лежат рядом:

| Файл | Что делает |
|------|------------|
| `_apk/real_login.py` | вход готовым аккаунтом, доводит до спавна, шлёт `/mm` |
| `_apk/raw347.py` | дампит сырые байты входящего RPC 347 |
| `_apk/mm_oracle.py` | оракул закрытия, фиксированный список вариантов |
| `_apk/mm_brute.py` | перебор диапазона RPC-id, находит рабочий |
| `_apk/mm_verify.py` | подтверждает семантику `list_item` на двух пунктах |
| `_apk/mm_botpath.py` | проверяет штатный `session.send_dialog_response` |
| `_apk/mm_live.py` | сквозной прогон: `/mm` → ответ → разбор статистики |

Перебор (если понадобится заново):

```bash
BR_TEST_MODE=1 python3 -u _apk/mm_brute.py <ник> <СЕРВЕР> socks5://127.0.0.1:20013 300 460
```

`mm_brute.py` перебирает id, печатает любую реакцию и сам подтверждает найденный
id повторным `/mm`. Один прогон — около 4 минут на 160 значений.

**Важно:** перебор имеет смысл только с правильным конвертом. Я один раз
потеряла полчаса, потому что слала `PacketBuilder.create(0x20, …)`, а
`PacketID.RPC` = **`0x0B`**. Все ручные RPC улетали в мусор и «не работали».
Собирать конверт только через `PacketBuilder.rpc(body)`.

## 8. Требования, без которых не работает ничего

1. **Бот должен быть на спавне.** `pos = (0,0,0)` или зона авторизации — меню
   не придёт. Проверка: `logic/spawn.py:is_spawned_position(pos)`.
2. **Не регистрация, а вход.** Новый ник = регистрация, там другой поток.
   Нужен существующий аккаунт с паролем.
3. **Чистый exit-IP.** Бан BR привязан к паре exit-IP + сервер. Забаненный хост
   отдаёт `Ожидание (21:02)` и до мира не доходит. Рабочий прокси на момент
   проверки: `20013` (Турция). Перебирать так:
   ```bash
   BR_TEST_MODE=1 python3 -u _apk/world_test.py VORONEZH socks5://127.0.0.1:20013
   ```
4. **Пауза перед ответом.** Мгновенный ответ в тот же тик, что пришёл диалог,
   ловится античитом (кик кодом 25). В коде стоит `random.uniform(0.35, 0.9)` сек.

## 9. Карта кода

| Файл | Что там |
|------|---------|
| `samp/constants.py` | `RPC.DIALOG_RESPONSE = 406` — номер ответа |
| `samp/packets.py` | `RPCBuilder.payload_dialog_response` — раскладка payload (§3) |
| `samp/sender.py` | `"dialog_response": (REL, PRI_SYS, 0)` — доставка |
| `samp/session.py` | `send_dialog_response()` — штатная отправка |
| `samp/parsers.py` | `RPCParser.show_dialog` — разбор входящего RPC 347 |
| `logic/menu.py` | `decide_stats_flow`, `parse_rows`, `strip_colors`, `parse_stats` |
| `logic/menu.py` | `MenuAnswerer.answer` — защита от повторных ответов по отпечатку |
| `bot.py` | обработчик `onShowDialog`, ветки `pick` / `close` |

### Ловушка в `decide_stats_flow`

Раньше функция начиналась с `if not stats_pending: return None`. Флаг ставил
только таймер статистики, поэтому `/mm`, отправленный **вручную**, оставался
без ответа: диалог висел поверх игры, и сервер на любую следующую команду
отвечал «Закройте диалог!».

Теперь меню игрока отвечается **всегда**, независимо от `stats_pending`.
`stats_pending` влияет только на разбор экрана статистики.

## 12. Капча — id 26

Разобрана заодно, чтобы не искать второй раз.

**Входящее:** JSON интерфейс 26, ключ **`"u"`** — URL картинки.
Картинки в APK нет, она всегда приходит с сервера.

**Ответ:**

```python
session.send_json(26, {"t": 0, "s": "<текст с картинки>"})
```

| Ключ | Что означает |
|------|--------------|
| `t` | тип ответа, всегда `0` |
| `s` | распознанный текст |

Поведение клиента: кнопка «Готово» неактивна (alpha 0.3), пока поле пустое;
после клика `R.anim.button_click`, пауза **400 мс**, потом отправка.
`onDismiss` тоже отправляет, если `dontSend == false`.

Разметка окна: `res/layout/br_new_captcha.xml`, 300dip × wrap, картинка
240×120dip, поле ввода `maxLength=20`. Имена id в APK с опечатками:
`br_new_captha_img`, `br_new_capcha_ok`, `br_new_caphca_line` — так и есть,
это не моя ошибка.

Распознавание: `captcha_solver.py` (чистый Pillow, без numpy/cv2).
Банк шаблонов построен на системных шрифтах — на синтетике 97.9% по символам,
но на живом шрифте BR точность будет ниже. Лечится `learn("видимый_текст", img_bytes)`.

## 13. Итог

```
входящее меню : RPC 347, dialog_id=0, style=2, пункты в info через \n
ответ         : RPC 406, payload 00 00 | resp | list_item | 00
                resp: 1=Выбрать, 0=Закрыть
                list_item: индекс строки с нуля
доставка      : RELIABLE + SYSTEM_PRIORITY
```

Этого достаточно, чтобы отвечать на любое меню BR. Всё остальное в файле —
чтобы не проходить путь заново.
